
### P0-2. `Participant`에 `user_id`가 없다 — 조인이 끊겨 있다

```python
# models/participant.py — 현재
id      : str   # participant PK
room_id : str
nickname: str
is_host : bool
```

```python
# models/axis_score.py — user_id로 조인해야 하는데
user_id : str   ← Participant에 이 컬럼이 없다
```

**축 점수를 저장해도 누구 건지 찾아갈 수가 없다.** 스키마 결함이다.

그리고 `participants.id`는 **방마다 새로 생긴다.** 같은 사람이 팀플 방과 연인 방에 들어가면
서로 다른 id가 된다. "팀플의 나 vs 연인의 나"가 원천적으로 불가능해진다.

**할 일**
```python
class Participant(Base):
    id      : str          # 이 방에서의 참가 기록
    user_id : str          # ← 추가. 사람 그 자체. 방이 달라도 유지
    room_id : str
    nickname: str
    gender  : str          # ← 추가. 합석 짝 매칭에 필요
    is_host : bool
```


## 3. 최근 결정 반영 — 뼈대에 아직 없는 것

기획안 회의에서 나온 내용이라 뼈대가 모를 수밖에 없다. 브랜치에서 같이 반영한다.

| 결정 | 반영할 곳 |
|---|---|
| **서비스 이름 = 얼음땡(가제)** | `TopBar` "CREWVERSE" · `SharePage` 하단 · `index.html` title · README |
| **연인 등급명 분리** | `mockReport.js`의 `GRADE_LABEL`이 단체용 하나뿐이다. `S 환상의 궁합` / `F 환장의 궁합` 세트가 따로 필요 |
| **MBTI 폐기** | 입력은 **닉네임 + 성별**만. `StartPage`에 성별 추가 |
| **칭호 개별 숨김 없음** | 리포트에 숨김 버튼을 만들지 않는다 |
| **`PLN` 순서 정하기** | 1단계 이지선다 10개 중 2개를 순서 정하기로 대체. 측정은 **결과가 아니라 과정**(첫 입력까지 시간, 재배열 횟수) |
| **한 명 이탈 시 진행** | 호스트가 기다릴지 넘길지 고르고, 안 돌아오면 그 시점 데이터로 확정 |
| **복구 링크 없음** | 트러블슈팅 문서로만. 기능 만들지 않는다 |

## 4. 이 브랜치에서 잡을 순서

```
1  api/client.js + user_id 발급 · localStorage        P0-3, P0-1 기반
2  Participant에 user_id · gender 추가 + User 모델     P0-2
3  방 생성·입장·대기실을 서버 연동으로 교체              P0-1
4  설문 18문항 (팀플) + 제출 API                       P1-1
5  Stage 인터페이스 + 1단계 실제 구현 + 폴링 동시 공개   P1-2, P0-4
6  축 산출 → 유형 판정 (룰만. LLM 없음)                기획안 §6
7  2~4단계
8  칭호 · 궁합 계산
9  LLM 리포트 + 폴백
```

**1~3번이 끝나야 나머지가 붙는다.** 지금은 저장할 곳이 없어서 게임을 만들어도 결과가 안 남는다.

> 기획안 §17의 원칙은 그대로다 — **팀플 하나를 끝까지 뚫고 나서 나머지를 수평 확장한다.**
> 합석·낮·밤은 사전 파일과 문항만 갈아끼우면 되므로, 팀플이 돌기 전에는 손대지 않는다.
